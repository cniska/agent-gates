# agent-gates

Installs commit gates into a project and judges their health. [`README.md`](README.md) lists every gate with a summary of what it refuses, and [`docs/`](docs/) states those refusals in full and holds the rest: how the gates judge, the commands, the plugin, development and releasing. Every release goes through `scripts/release.sh <patch|minor|major>`, run by `cniska-skills:ship`. [`SPEC.md`](SPEC.md) states what must hold and changes in the same commit as the behavior it describes.

## Rules

- `bun run check` is the check: lint, typecheck, knip (unused exports, files and dependencies) and tests. It passes before every commit.
- `src/README.md` maps the modules and their boundaries; `src/modules.test.ts` lists each module's public files and holds the boundary.
- `gates/` holds each gate file as it is installed. A change to a file's bytes bumps the version in its `agent-gate:<part>:<version>` marker and appends that version's hash to the file's `versions` in `src/gates-contract.ts`; the registry tests in `src/gates.test.ts` hold both, and the earlier hashes let install update an unedited file without setting it aside. `gates/no-comments/*.cjs` and `gates/no-secrets/scan.cjs` are bundled from `src/` by `bun run gates:bundle`, taking their marker from `GATES`, so a change to their sources bumps the version first, then bundles; a test fails while a bundle is stale. The adapters bundle the gate names, so a new gate bumps every adapter too. Then `bin/agent-gates install` brings this repo's own gates up to date, and a test fails until it has.
- `plugin/` is the optional Claude Code plugin. Its hooks run in other people's sessions, so they stay bash needing only `jq`, `node`, git and the base system, and do nothing in a checkout without the gates they serve. They never block an edit, gate files included, since install needs them; the one block is a git command that skips the gates. `acceptance/plugin.acceptance.ts` holds that contract.
- A README gate row summarizes what the gate refuses, checked against the gate's hook, workflow and FRs; the full statement lives in `docs/gates.md`, `docs/no-comments.md` for the no-comments gates, or `docs/no-secrets.md` for `no-secrets`.
- A file several gates share carries a shared part (`githooks`, `no-comments`), never a gate name, so it does not read back as a chosen gate.
- Fix the cause, never work around it, and add no debt. Debt you find is fixed where it is found.
- This repo requires no other cniska tool, and names none of them, nor any of their skills, agents, plugin installs or report shapes, in src, acceptance, SPEC, README, plugin, scripts, npm, docs, gates, bin, the workflows or tests. The one exception is the marketplace address `cniska/agent-skills`, which the plugin's install names. `scripts/standalone.test.ts`, in the check, refuses the names it knows.
- Code carries no comments, tool contracts aside. A why goes into a name, a test, or this file.
- Work each task on a topic branch in its own worktree. Commit each slice there, in Conventional Commits, once `bun run check` passes and a fresh reviewer accepts it, and push the branch after each. The message is the subject line alone: no body, no trailers. The user stays the author.
- Land a task as a whole, with no pull request: once a fresh reviewer, given the branch's whole diff against `main`, accepts it (for a one-commit branch, that commit's accept), fast-forward `main` to the branch, push `main` and delete the branch on origin. That accept is the owner's standing sign-off, so no landing waits on them. A release is not a task: its tag, and any commit `scripts/release.sh` makes, stay on `main`.
